The idea

A dependency is other people's code inside your program

Every line in requirements.txt is a dependency (a library that your program needs to run). A dependency runs with the same rights as your own code. This means a dependency can do anything your code can do.

Direct: you import it. Indirect: your library needs it. For example, requests uses urllib3 to send web requests. You never import urllib3 or idna. But these two libraries still run inside your program.

The risk

Other people's code costs no money. But their code can have security problems. When you install their library, those problems come into your program too. So you must check the libraries you use.

How a problem becomes known

From one bug to a warning on your screen

1

Someone finds a bug. For example, a researcher sees that a library can show a password to other people.

2

The researcher tells the maintainers (the project owners) privately. The file SECURITY.md says how.

3

Then a fixed version comes out. For example 5.3 → 5.3.1.

4

Next, an advisory comes out (a public notice). The advisory says which versions have the bug and which version fixes it.

5

Databases store the advisory. Tools like pip-audit and Dependabot read these databases.

Why step 2 is private

Everyone can read a public issue. So if someone posts the bug there first, attackers learn about the bug before a fix exists. Because of this, a good project has a file called SECURITY.md. This file tells you where to report a security problem.

Reading the names

One problem, three names

Several databases store the same advisory. Each database gives the advisory its own ID. So the three IDs in this table are not three different problems:

IDWho gives itWhere you see it
CVE-2020-1747CVE, the world-wide list of known vulnerabilities (security problems)News and every database
GHSA-6757-jp84-gxfxGitHub Advisory DatabaseDependabot alerts on GitHub
PYSEC-2020-96Python Packaging Advisory Databasepip-audit output

All three rows are the same problem in PyYAML 5.3. PyYAML can read a YAML file with its full loader. Suppose your program uses the full loader on a YAML file from a stranger. Then hidden code in that file can run. Fixed in 5.3.1.

OSV

osv.dev (Open Source Vulnerabilities) puts the data of these databases in one place. So you can open the osv.dev page of any ID. On that page, the Aliases line lists the other IDs of the same problem.

The tool on GitHub

What Dependabot does

Dependabot is a GitHub feature. First, Dependabot reads the dependency files in a repository, such as requirements.txt. Then Dependabot compares every version with the GitHub Advisory Database.

Both tools use the same kind of databases, so they give the same warnings. But Dependabot runs on GitHub, and pip-audit runs on your PC.

  • Job 1 · Alerts. If a version you use has an advisory, an alert appears in the Security and quality tab. The alert shows the package, how serious the problem is, and the fix version.
  • Job 2 · A fix as a pull request. Dependabot can open a pull request (PR) that changes the version line. But a person still reads the PR and runs the tests. Then this person decides to merge or not (Chapter 5).
Why I show it on my screen

GitHub shows Dependabot alerts only to people who manage the repository. Your account in the course organization does not have this permission. So you use pip-audit on your own PC, and the instructor shows Dependabot on the screen.

The tool on your PC

Reading pip-audit output

First, pip-audit reads a requirements.txt and finds every library that these lines need. Next, pip-audit asks a vulnerability database about each library. pip-audit does this work in a temporary place and then deletes that place. So pip-audit installs nothing into your .venv (the folder that holds your project's libraries, Chapter 3).

What to do about it

The fix: use a newer version, then test again

pip-audit showed old versions with known problems. You fix each package in three steps:

Step 1

Find

Look at all rows of the package. Find the highest number in the Fix Versions column.

Step 2

Change

In requirements.txt, write that version or a newer one.

Step 3

Test

Run pip-audit again. Then run your program and the tests, because a new version can work a little differently.

One change is not always enough

Slide 7 shows that urllib3 1.23 is fixed in 1.24.2. But requests 2.19.1 works only with a urllib3 older than 1.24. So you must also change requests to a newer version.

Pinned is not the same as safe

Today, every version on the course whitelist passes pip-audit. But a pinned version (Chapter 3) gets old, and new advisories come out often. So run pip-audit again before every release (every new version of your program).

Before you add a library

Five checks for choosing a library

Advisories tell you about problems that people already know. But these five checks show whether someone will fix the next problem.

Recent commitWhen did the code last change? Look at the line above the file list. Years without a change is a warning sign.
PeopleFind the Contributors number on the right side of the page. If only one person works on the project, the project stops when that person stops.
SECURITY.mdOpen the Security and quality tab. Is there a security policy, or does it say No security policy detected?
LicenseFind the license name on the right side of the page. Then ask (Chapter 7): is this license permissive (MIT, BSD, Apache)?
Issue responseOpen the three newest issues. Did anyone other than the writer answer?

A secret is not code

Keep secrets out of your code

An API key is a password that lets a program use a service. Suppose you write an API key inside a .py file. With your next push, the key goes to GitHub. On a public repository, anyone can then copy the key.

.env stays on your PC. The code asks for the key by name. GitHub gets the code, never the key.

import os
from dotenv import load_dotenv

load_dotenv()
key = os.getenv("API_KEY")
  • from dotenv import load_dotenvThe library python-dotenv. In code its name is dotenv.
  • load_dotenv()Reads the file .env. This file has one secret per line, like API_KEY=....
  • os.getenv("API_KEY")Asks for the value by name. So the value itself is never in the code.
If a key was pushed once

Deleting the file in the next commit is not enough, because the old commit still has the key. So think of that key as stolen. Cancel that key and make a new key.
