Why version control

report_final_v2_really_final.docx

Everyone has a folder like this. Five copies of one file, and nobody remembers which one is the real one, or what changed between them.

Without Git

Copies with new names

You save a new copy every time you are afraid to lose something. The names grow longer. You cannot see what changed, who changed it, or why.

With Git

One file, a list of saved versions

There is only one report.docx. Git keeps every saved version behind it, each with a short note: what changed and why. You can go back to any of them.

From Chapter 3

You installed Git and only read its version number. VS Code is where you write, Python is what runs, and Git is what remembers. Today you use it for the first time.

The first word

A repository is
a folder plus its history

A repository (repo) looks like a normal folder: your files are inside. The difference is a hidden folder named .git. That is where Git keeps every saved version of every file.

What you see

Your files

README.md, notes/, your code. You open and edit them the same way as any other file.

What Git keeps

The history

Inside .git: every commit, in order. You never edit this folder by hand. Git commands read and write it for you.

In this course

We always make a repository on GitHub first, then copy it to this PC. We never start one on the PC with git init. That way the branch name is main on both sides, from the first minute.

The main idea of today

Three states of a change

Your file never leaves your folder. What changes is its state — what Git has recorded about your change. Two commands change the state.

State 1

Modified

You edited a file. Git sees the change but has not recorded it yet. git status calls it Changes not staged for commit.

State 2 · git add

Staged

You chose this change for the next photo — one file or several: git add a.md b.md. git status calls it Changes to be committed.

State 3 · git commit

Committed

The photo is taken and kept in the history, with a short ID and your message. git status says nothing to commit, working tree clean.

Why two steps

You changed five files, but only two belong together. git add lets you choose those two, and one commit holds both. One commit = one idea, not one file. Your commit history then reads like a list of what you did.

Getting the repository

clone: copy the whole album
to this PC

git clone copies a repository from GitHub to this PC: every file and the whole history. The new folder already knows where it came from.

git clone https://github.com/<your-username>/oss-practice.git
Cloning into 'oss-practice'...

cd oss-practice
git log --oneline
2c359be Initial commit

How to read these boxes: a line that starts with $ is what you type (do not type the $). The grey lines are what Git prints back.

  • The folder name comes from the repository name — here, oss-practice.
  • The GitHub copy is called origin. Git remembers it, so later you only type git push and git pull.
  • Your 7-character code is different from 2c359be. Every commit gets its own code.

Taking a photo

status → add → commit

Before and after each step, ask Git where things are with git status. These lines come from a real run on a Windows PC.

git status
Changes not staged for commit:
        modified:   README.md

git add README.md
git status
Changes to be committed:
        modified:   README.md

git commit -m "Add about me"
[main bbe6d57] Add about me
 1 file changed, 3 insertions(+)
A good message

A short line about what you changed, starting with an English verb: Add about me, Update notes, Fix typo in README. Not asdf, not final. You will read these lines later.

Two copies of the album

push sends, pull brings back

After a commit, the new photo is only on this PC. GitHub has not seen it yet.

This PC → GitHub

git push

Sends your new commits to GitHub. Before the push, git status says Your branch is ahead of 'origin/main' by 1 commit. After it, up to date.

GitHub → this PC

git pull

Brings commits that are on GitHub but not here — for example a change you made in the browser. Git prints Fast-forward when it simply adds them on top.

git push
 ! [rejected]        main -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. ...  use 'git pull' before pushing again.
If push is rejected

GitHub has a commit you do not have yet. Nothing is lost. Run git pull --no-edit, then git push again. The hint in the message says the same thing. --no-edit keeps Git from opening a text editor for the merge message.

Whose commit is it?

Every commit carries a name

Git writes a name and an email into every commit. On a new PC it does not know you yet, so your first git commit stops with this message:

Author identity unknown

*** Please tell me who you are.

Run

  git config --global user.email "you@example.com"
  git config --global user.name "Your Name"

to set your account's default identity.
Omit --global to set the identity only in this repository.

fatal: unable to auto-detect email address (got 'Administrator@<PC name>.(none)')
In this room: no --global

Every PC here shares one Windows account, so --global would write your name for the next student too. Read the line that starts with Omit: leave out --global.

git config user.name "<your GitHub username>"
git config user.email "<ID+username@users.noreply.github.com>"

Name = your GitHub username. It is already public in your repository address. Email = not your real one, but your noreply address: GitHub made it for you, it still counts the commit as yours, and nobody sees your real email. Find it: avatar → Settings → Emails → the text under Keep my email addresses private.

Same thing, with buttons

VS Code Source Control
runs the same commands

The Source Control view (Ctrl + Shift + G) is not a different tool. Each button runs a Git command you already know.

Button in VS CodeSame as
+ next to a file (Stage Changes)git add <file>
Message box, then ✓ Commitgit commit -m "..."

Why learn both

Buttons are faster. Commands show you what is really happening, and they work on every computer, with or without VS Code. When a button fails, the error is a Git error — and you can read it now.

Reading the history

git log --oneline:
one commit per line

The newest commit is at the top. Each line is a short code and a message.

git log --oneline
eb2f5c3 Add chapter 4 notes
8b54b3a Update README.md
bbe6d57 Add about me
2c359be Initial commit
  • Bottom line — GitHub made it when you created the repository with a README.
  • Update README.md — GitHub wrote this message for you when you edited the file in the browser.
  • The code on the left is the short ID of that commit. You use it later to point at one commit.

PART 3

Pull a change, then the same loop with buttons

25 min

A change made on GitHub comes back with git pull. Then you do add, commit and push again — this time with the VS Code buttons.

  1. On GitHub, open README.md in your repository and click the pencil icon (edit). Change one line — for example, add one more reason why you like your project.
  2. Click Commit changes, keep the message GitHub suggests (Update README.md), and click Commit changes again. What is happening: This new photo is only in the GitHub copy. The README.md on your PC has not changed.
  3. Back in the VS Code terminal: 
    git pull
    You see Fast-forward and a line with README.md. The change you made in the browser is now in your file. What is happening: Git downloads the new commit from origin and adds it on top of your history, then updates your file. You had no new commits of your own, so Git only moves forward — that is what Fast-forward means. No extra commit is made.
  4. Now the buttons, all inside VS Code. Look at the narrow bar on the far left of the VS Code window. Click the first icon (two pages, Explorer — the file list, Ctrl + Shift + E). There, make a folder notes and inside it a file ch04.md. Write two or three lines: what git add and git commit do, in your own words. Save.
  5. In the same left bar, click the third icon, under the magnifying glass: three small circles joined by lines. That is Source Control (Ctrl + Shift + G). It shows a small number — how many files changed. Hover over ch04.md and click + (Stage Changes). The file moves to Staged Changes. What is happening: VS Code runs git add on this file for you. Staged Changes is the staging area — the same list that git status calls Changes to be committed.
  6. Type Add chapter 4 notes in the message box and click ✓ Commit. What is happening: VS Code runs git commit with the message you typed. The photo goes into the history on this PC only — GitHub does not have it yet.
  7. Click Sync Changes. VS Code says This action will pull and push commits from and to "origin/main". Click OK. What is happening: VS Code runs git pull first, then git push. The pull brings any new photos from GitHub first, so the push is not rejected.
  8. If VS Code asks about periodically run "git fetch" now, click Yes.
  9. In the terminal, type git log --oneline. You should see four lines, newest on top.
