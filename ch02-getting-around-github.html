The core concept

A repository is a project's home —
code, history, and conversation, together

Everything a project needs is inside its repository. This means more than the code. It also means the full history of how it got here, and the discussion about what comes next.

Code

What it is, right now

The files as they are today — the thing you would download and run.

History

How it became what it is

Every commit (one saved change) ever made, who made it, and why. No change is ever hidden.

Conversation

Where it's going next

Issues and pull requests are where people discuss the project in public. A pull request is a request to add your change to the project.

Reading the page

The parts of a repository page

Code

Code tab

The files on the branch (a separate line of work) you are viewing. Click a file to read it, click a folder to go deeper.

Issues

Issues tab

Bug reports, feature requests, and questions — the project's open to-do list and its ongoing conversation.

PRs

Pull requests tab

Proposed changes waiting for review. Each one is someone asking "can this become part of the code?"

CI

Actions tab

Automated checks (CI, short for Continuous Integration) that run on every change — tests and builds. Green means they passed.

Stats

Insights tab

Charts of activity — contributors, how often people commit, how many people visit. Check here to see if a project is still active.

Sidebar

About box

One-line description, topics/tags, license, and the README (the project's introduction file) shown as a page — read this box before anything else.

Your screen may show more tabs

A repository can also show Discussions, Projects, Wiki or Security. Those are optional — the maintainers turn them on. The six above are in every project. A missing tab tells you something too: our own course-notice has Issues turned off, because it is only for announcements. (It is private, so it shows 404 unless you are signed in — see the FAQ.)

First thing to read

The README is the first thing you read

A good README answers five questions before you've even opened a single code file. If it cannot answer these in 30 seconds, that tells you something too.

  • What — what does this project actually do, in one sentence?
  • Why — what problem does it solve that made someone build it?
  • Install — which command do I type to install it?
  • Usage — is there example code that shows how to use it?
  • License — am I allowed to use it? (Chapter 7 covers this in detail.)
Try it now

Open any repo's README and check the clock. Can you answer all five in one minute? If not, the README is weak — even if the code itself is good.

A common mistake

Stars are popularity,
not quality

A star means someone liked it once. It does not mean the code is good, safe, or still maintained today.

More than bug reports

Issues are the project's conversation,
not just a bug list

More than bugs

Issues hold bug reports — but also requests for new features, design questions, and "has anyone tried this?" discussions. Read a project's Issues tab and you are reading its whole conversation.

Labels tell you where to start

Maintainers tag issues to sort them. Two labels matter most to you right now. good first issue means it is small and easy for beginners. help wanted means the maintainer wants outside help.

Where to look: the Issues tab, then the Labels button.

The template for today's assignment

The parts of a good issue

A good issue is one a stranger can read, understand, and act on — without asking you anything. Four parts, every time.

Title

Clear enough to search for later. "Crashes on empty input" is better than "bug".

Context

What were you doing, on what version, on what system? Enough that someone else could see the same problem.

Steps

The exact steps that cause it — numbered, in order, nothing left out.

Expected vs actual

What you thought would happen, and what actually happened instead. That difference alone often shows what is wrong.

A repeatable routine

How to read a project
without reading everything

You will never have time to read every line. Here's the order that gets you 90% of the understanding in 10% of the time.

READMEWhat it does, why, and how to run it — always read this first.
About box + topicsThe one-line description and tags tell you the topic in seconds.
IssuesWhat is broken or being discussed right now — what the project is really like, not what it says about itself.
Recent commitsIs anyone actually working on this, and on what?
CONTRIBUTING.mdIf you plan to change the code, this file tells you the rules first — so you do not spend time on the wrong thing.

Use the template

Peer review

Comment on two other students' issues

Reading and answering someone else's issue is half of how people work together on GitHub.

  1. Find two issues written by people in your row, in practice-pr › Issues.
  2. Write one comment on each. Ask a real question — not just "nice project!". For example: "When was this project last updated?" or "What would you use this for in your own project?"
  3. Reply to any question left on your own issue before the deadline.
Grading

How it's graded

We do not grade your coding skill. We look at whether you did the work, and whether you can explain it.

Complete

Issue follows the template, all four sections are your own words, and you left two specific peer comments.

Partial

The issue is there, but a section is missing, too general, or copied. Or the comments on other students are missing or too general ("nice!").

Not submitted

No issue by the deadline. Late submissions still get partial credit.

You must explain it

This is true for every mini assignment this semester. If you can't explain why you picked this project, it doesn't count as complete. This is true even if the issue text looks right.
