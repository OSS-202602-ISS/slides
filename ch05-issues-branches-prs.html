Step 1 of the loop

An issue is a conversation
about one piece of work

Before anyone writes code, somebody writes down what needs to be done. That note is an issue. It gets a number, and everybody can read it, comment on it and link to it.

A title

What the work is

One short line. [Task] Add intro page for 20261234 tells the whole team what is coming.

A number

#999, #1000, #1001

GitHub numbers every issue. Later you write #999 and GitHub turns it into a link to that issue.

A conversation

Questions before code

"Should this be one file or two?" is cheap to answer in an issue. It is expensive to answer after the code is written.

You already did this

Your Chapter 1 to 4 assignments were issues in practice-pr. Today you open one for a different reason: to say "I am going to do this work" before you start it.

Step 2 of the loop

A branch is a parallel copy

A branch starts on your PC, as an exact copy of main. You commit on your branch, and main does not change — not on your PC, not on GitHub. Everyone in the class can have their own branch at the same time without touching each other.

main

Your line

Your commits go here. Nobody else sees them in main on GitHub until you ask, and somebody says yes.

Switched to a new branch 'intro/20261234' — and after that, git branch (on your PC) puts the * next to your branch, not next to main.

Why we do not push to main on GitHub

If you push straight to main on GitHub,
it breaks for everyone

In Chapter 4 you pushed to main on GitHub, in your own repository. That was fine — you were the only person there. In a shared repository, main on GitHub is what everyone pulls to their PC. One mistake in it is now on everyone's PC.

One mistake in main on GitHub goes to every PC.

No review

Nobody looked

A typo, a deleted file or a password goes in without anyone else looking at it.

Hard to undo

Others build on it

After others have pulled and committed on top of it, undoing it is slow work for the instructor.

The rule in this room

You have Write access to practice-pr, so GitHub will not stop you from pushing to main on GitHub. The rule stops you: never push to main on GitHub. If it happens, tell the instructor at once — it can be undone, but only if we know.

Step 4 of the loop

A pull request says
“please merge this”

A pull request (PR) is made on GitHub. It is a request to join your branch (the one you pushed to GitHub) into main on GitHub. It shows exactly which lines changed, and it gives other people a place to comment before anything is merged.

What it holds

Your branch + a description

The commits on your branch, the changed lines (the Files changed tab), and a short description that you write.

What happens next

Review, then merge

Someone reads the changes and comments or approves. Only then does anyone press merge. Until that moment, main on GitHub is safe.

The name

"Pull request" means: I am asking you to pull my changes in. On GitHub you see it as the Pull requests tab of a repository.

The whole picture

The loop: six steps

Almost every open source project works in this loop. You do the first four steps today. Steps five and six are Chapter 6.

Today you stop at step 4

Do not merge your pull request. It stays open until Chapter 6, when a partner reviews it first.

Names matter

Your branch name:
intro/<StudentID>

A branch name tells the team whose work it is and what it is for, before anyone opens it. After everyone pushes, practice-pr on GitHub will have one branch for each student. The name is how you find yours.

intro/20261234        good: what it is / whose it is
my-branch             bad: whose? for what?
intro 20261234        wrong: a branch name cannot have a space
  • The first part says what kind of work — intro for today's intro page.
  • The second part says whose — your student ID, because practice-pr is private to this class.
  • The team project uses a different first part (feature/...). The pull request checklist mentions that one. Today it is intro/.

Writing the request

A good PR description:
three lines

The reviewer did not watch you work. Three lines tell them everything they need before they open a single file.

WhatWhat this pull request changes. "Adds my intro page and one line in INDEX.md."
WhyWhich issue it answers, and why the work is needed. "So the class list links to my page."
How to checkWhat the reviewer should open or run, and what they should see. "Open Files changed: two files, four lines in my page, one new line in my row of INDEX.md."
Not a letter

No "Dear sir". No "please kindly". Short and exact is polite in a pull request.

Linking the two

Closes #N ties the PR
to its issue

Write Closes #999 in the pull request description, with your own issue number. GitHub links the pull request and the issue to each other.

Right away

A link both ways

On the right side of your pull request, under Successfully merging this pull request may close these issues., you see your issue.

When it is merged

The issue closes by itself

Nobody has to remember to close it. The work and the conversation about it end together.

Exactly this form

Closes #999 — the word, one space, the #, the number. Your issue stays open today, because the pull request is not merged yet. That is correct.

PART 2

A branch, two files, one push

30 min

Make your own branch before you change anything. Then add your page, add one line to the class list, and push the branch.

  1. Make your branch and move onto it: 
    git switch -c intro/20261234
    You see: Switched to a new branch 'intro/20261234' What is happening: Git makes a parallel copy of main and moves you onto it. Your files do not change. From now on your commits go on this branch, and main stays as it is.
  2. Check where you are: 
    git branch
    * intro/20261234
  main
    The * must be next to your branch. If it is next to main, go back to step 1.
  3. In the VS Code file list on the left, open practice-pr, right-click the intros folder and choose New File…. Name it 20261234.md (your ID).
    D:\oss\20261234 └─ practice-pr ├─ .github ├─ intros │ ├─ INDEX.md │ └─ 20261234.md ← new file (your ID) └─ README.md

    Your new file goes inside intros, next to INDEX.md.

    Copy these four lines into it and replace the words in brackets: 
    - **Name:** (your name only - no phone number, no email)
- **Country:** (your country)
- **Favourite open source project:** (project name) - (one reason)
- **My goal this semester:** (one sentence)
    • Your name only. No phone number, no email, no address.
  4. Open intros\INDEX.md. It has one part for each row of the room: ## Row A to ## Row J. Find your own row: the instructor shows the row letters on the screen — find your name there. Add one line right under the comment in your row, with your ID in both places. Do not change any other line. 
    ## Row C

<!-- add your line below this comment -->
- [20261234](20261234.md)
    What is happening: your page is a new file that only you touch. INDEX.md is one file that the whole class changes. It has one part for each row, and you add one line in yours. When two people change the same place in a file, Git cannot join the two by itself — you see this in Chapter 6.
  5. Save both files (Ctrl + S). Then look at what Git sees: 
    git status
    On branch intro/20261234
Changes not staged for commit:
        modified:   intros/INDEX.md

Untracked files:
        intros/20261234.md
    (Git also prints some help lines in brackets. The four lines above are the ones to check.)
  6. Stage both files and commit: 
    git add intros/20261234.md intros/INDEX.md
git commit -m "Add intro page for 20261234"
    You see a line that starts with [intro/20261234 and then 2 files changed. What is happening: the commit goes on your branch only. main stays exactly as it was. Nothing is on GitHub yet — the commit is only on this PC.
  7. Push your branch to GitHub. The first push of a new branch needs -u origin and the branch name: 
    git push -u origin intro/20261234
    Look for these two lines in the output: 
    branch 'intro/20261234' set up to track 'origin/intro/20261234'.
 * [new branch]      intro/20261234 -> intro/20261234
    If push says permission denied (403), call the instructor — do not retry with another account. What is happening: Git sends your branch and its commit to the GitHub copy (origin) as a new branch with the same name. main on GitHub does not change. -u connects your branch to the one on GitHub, so next time, on this branch, a plain git push is enough.
If you committed on main by mistake

git status says On branch main and Your branch is ahead of 'origin/main' by 1 commit. Do not push. Move the commit to a new branch, then put main back the way GitHub has it:

git switch -c intro/20261234      the new branch takes your commit with it
git switch main
git reset --hard origin/main      main is now the same as GitHub's main
git switch intro/20261234         back to your branch; your commit is here

Then push your branch as in step 7. If you have not committed yet, only the first line is needed: git switch -c takes your changes that are not committed yet with it.
