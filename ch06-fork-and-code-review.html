How to fix someone else's code politely — by review, and by solving a conflict.
A fork is your own copy of someone else's repository.

Clone

A copy on this PC

You did this in Chapter 4. The copy lives in a folder on the computer in front of you.

Branch

A side line inside one repository

You did this in Chapter 5. Same repository, a separate line of commits.

Fork — new today

A copy on GitHub, in your account

A whole repository, copied from someone else's account into yours. You can change it freely. The original does not change.

The contribution flow

Fork, clone, branch,
then ask with a PR

In practice-pr you have Write access, so you made a branch inside it. On a stranger's project you have no Write access. So you work in your own copy, and ask the owner to take your change.

ForkOn GitHub, copy the project into your account. The original project is now called the upstream (the place your copy came from).
CloneCopy your fork to this PC. Not the upstream — you cannot push there.
BranchMake a branch for one change, commit, and push it to your fork. The same commands as Chapter 5.
Pull request to the upstreamOpen a PR from your fork's branch to the upstream's main. The owner reviews it and decides to merge — or not.
Your assignment

You do exactly this today, with your partner's oss-practice as the upstream. Every real open source contribution starts with these four steps.

Code review

Three kinds of review comment

A review comment is read by a person. Be specific, and be kind. A comment like "bad" or "good job!" helps nobody, because the author cannot act on it.

Question

Ask what you do not understand

Why did you choose ...?
What happens if ...?
Could you explain line 3?

Suggestion

Say one change, and why

Could you add why you like it?
I suggest ... because ...
Maybe move this line to the top?

Praise

Name the good part exactly

This line is clear because ...
Nice example — I did not know ...

Comment on the code, not the person

Write "this line is missing a reason", not "you forgot the reason". Short English is fine. A polite question is the strongest review comment.

Merge conflict

Why a conflict happens:
two answers for the same line

intros/INDEX.md has one part for each row of this room: ## Row A to ## Row J. In Chapter 5, you added one line under the comment in your row's part. Then my own PR was merged, and it added one line under the comment in every row's part. Now, in your row's part, the same place has two different answers.

main now says

Under the comment: the instructor's line

Your branch says

Under the comment: your line

Git cannot choose

Git joins changes by itself when they touch different lines. When two branches change the same place, Git does not guess which one is right. It stops and asks a person. That stop is a merge conflict. It is not an error. Nothing is broken.

Reading the markers

<<<<<<<  =======  >>>>>>>

When Git stops, it writes both answers into the file and puts three marker lines around them. This is your row's part of the real file, from a real conflict on the instructor's PC. The other nine rows joined by themselves — only your row stops:

## Row C

<!-- add your line below this comment -->
<<<<<<< HEAD
- [20261234](20261234.md)
=======
- [teacher](teacher.md)
>>>>>>> origin/main
<<<<<<< HEAD

Start: your side

From here down to the ======= line is what your branch has.

=======

The middle

The line between the two answers.

>>>>>>> origin/main

End: the other side

Above this line, down from =======, is what main has.

Resolving it

Choose, then delete
the three marker lines

To resolve a conflict you edit the file so it says what it should say, and remove every marker line. For INDEX.md the right answer is easy: keep both lines in your row. Every line belongs in the list.

## Row C

<!-- add your line below this comment -->
- [20261234](20261234.md)    your line
- [teacher](teacher.md)      the instructor's line

PART A1

Review your partner's PR — ask for one change

15 min

Read your partner's intro file and ask for one specific change. You submit a review of the type Request changes.

  1. Open practice-pr › Pull requests and click your partner's PR (its branch is intro/<partner's ID>).
  2. You will probably see that the PR has a conflict. That is expected. Do not touch it — your partner resolves it in PART A3.
  3. Click the Files changed tab. Read intros/<partner's ID>.md. What is happening: this tab shows only what the PR adds or removes, not the whole repository. Green lines with + are new. The intro file is all green because the whole file is new; in INDEX.md only one line is green — your partner's line.
  4. Above the changed code, click Review changes. Write one specific request, using the patterns from the lecture. For example: 
    Could you add why you like it? One sentence is enough.
  5. Choose Request changes, then click Submit review. What is happening: GitHub saves your comment on the PR as a review with the result Changes requested, and your partner gets a notification. Nothing in the files changes — the author makes the change.
  6. Your partner now does the same on your PR. Wait for their request before you start PART A2.
Not allowed in a review

"Good job!", "OK", "LGTM" only, or a request the author cannot act on. Ask for a change the author can make in two minutes.

PART A2

Make the change your partner asked for

15 min

A review is a conversation. You answer it with a new commit on the same branch. The PR updates by itself when you push.

  1. Open your PR and read your partner's request in the Conversation tab.
  2. In VS Code, open the folder D:\oss\<your ID>\practice-pr. Open a terminal (Terminal › New Terminal) and go to your branch: 
    git switch intro/20261234
git status
    Use your own student ID. git status must say On branch intro/<your ID>.
  3. Edit intros/<your ID>.md the way your partner asked. Save. No phone numbers, no e-mail addresses.
  4. Commit and push: 
    git add intros/20261234.md
git commit -m "Add why I like it"
git push
    A small window Connect to GitHub appears — click Sign in with your browser. The browser opens; check the avatar is yours, then Authorize. What is happening: git push sends your new commit to the same branch on GitHub. A PR follows its branch, so the new commit appears in the same PR by itself — you do not open a new PR.
  5. On your PR page, reply to the review in one line, for example Done — I added one sentence. Please look again.
Do not fix the conflict here

Do not run git pull on main or git merge in this folder. You fix the conflict on GitHub in the next part. It is the shortest way for a conflict of one line.

PART A3

Resolve the conflict, get an Approve, merge

30 min

Keep both lines in INDEX.md, delete the three marker lines, and merge your own PR after your partner approves.

  1. On your PR page, scroll to the bottom and click Resolve conflicts.
  2. The web editor shows intros/INDEX.md with the markers. Change it so that both lines stay and the three marker lines are gone: 
    <<<<<<< ...                  delete this whole line
- [20261234](20261234.md)       keep
=======                         delete this whole line
- [teacher](teacher.md)         keep
>>>>>>> ...                  delete this whole line
    The words after <<<<<<< and >>>>>>> are branch names; they may be different from the lecture slide. The rule is the same: keep the list lines, delete the marker lines. If other students' lines from your row are there too, keep them all.
  3. Click Mark as resolved, then Commit merge. What is happening: GitHub makes a new commit on your branch, a merge commit: it brings everything new from main into your branch — the other nine rows join by themselves, and your row is what you just wrote. main does not change yet.
  4. Tell your partner: "Please approve." Your partner opens your PR › Files changed › Review changes, chooses Approve, and clicks Submit review. What is happening: Approve is the same kind of review as Request changes, with the answer “ready to merge”. It does not merge anything — the author still clicks the button.
  5. Now merge. At the bottom of your PR, click Merge pull request. If a different option is on the button, open the dropdown and choose Create a merge commit — not Squash. Then click Confirm merge. What is happening: GitHub adds one new commit to main, the merge commit. It joins the last commit of main and the last commit of your branch, so every commit of your PR comes into main with its history. Squash would put them in as one new commit instead.
  6. Open intros/INDEX.md on main and find your line. Your Chapter 5 issue closes by itself, because your PR says Closes #N.
The conflict came back?

If a student from your own row merged just before you, your row's part changed again, and your PR has a new conflict. Students in other rows never cause this. It can happen three times at most (your row has up to four people). Do steps 1–3 again — it takes one minute. In a busy repository this is normal.

No conflict on your PR?

If your PR page has no Resolve conflicts button, there is no conflict for you. This happens if you merged your PR already in Chapter 5, or you made your branch after the instructor's line was in main (for example, you did Chapter 5 at home). Skip steps 1–3 — the instructor's demo in the lecture showed you this part. You still review your partner, and your partner still reviews you. For the checkbox, "conflict resolved" means "I watched the demo".

Mini Assignment #6 · Explained today, done at home

Fork your partner's repository and send one PR

This is the contribution flow from the lecture, done for real: fork, clone, branch, pull request to the upstream. Your partner's oss-practice is the upstream.

Assignment

What to do

  1. Fork. Open https://github.com/<partner>/oss-practice and click Fork. You already have a repository named oss-practice, so in Repository name type a new name: oss-practice-<partner>. Click Create fork. What is happening: GitHub copies your partner's repository, with its history, into your account under the new name. Your partner's repository does not change. Your partner’s repository is now the upstream of your fork.
  2. Clone your fork into your own folder, then set your name and e-mail for this repository only (the same two lines as Chapter 4 — never --global): In VS Code: File › Open Folder… → D:\oss\<your ID> (at home: any folder), then Terminal › New Terminal. 
    git clone https://github.com/<you>/oss-practice-<partner>.git
cd oss-practice-<partner>
git config user.name "<your GitHub username>"
git config user.email "<your noreply address>"
    What is happening: Git copies your fork to this PC and saves its address under the name origin. So every git push from this folder goes to your fork, not to your partner's repository.
  3. Branch, change, push. Make the branch first. Then open README.md of the new folder in VS Code and fix one typo, or add one friendly line (for example, one open source project your partner might like). No personal information. A small window Connect to GitHub appears — click Sign in with your browser. The browser opens; check the avatar is yours, then Authorize. 
    git switch -c fix-readme
git add README.md
git commit -m "Fix a typo in README"
git push -u origin fix-readme
    What is happening: the new branch and its commit go to your fork on GitHub (origin). -u connects this branch to origin/fix-readme, so next time, on this branch, a plain git push is enough. Your partner's repository still has not changed.
  4. Pull request to the upstream. Open your partner's repository › Pull requests › New pull request › click compare across forks. Base: <partner>/oss-practice, main. Head: <you>/oss-practice-<partner>, fix-readme. Write the three lines from Chapter 5 (what, why, how to check), then click Create pull request. What is happening: the PR lives in your partner's repository and asks them to take the commits of fix-readme from your fork into their main. Their main does not change until they merge it.
  5. Submit. Open an issue in practice-pr with the Chapter 6 template — click here to open it with the template ready (sign in first). Title: [Ch06] StudentID Name.

When you receive a PR

Your partner sends a PR to your oss-practice. Leave one review comment on it — a question, a suggestion or a praise, as in the lecture. Merging it is your choice.

Links, not screenshots

Paste the PR link as text. The grader clicks it. Write under each heading — do not delete the headings.

Grading

How it's graded

We look at whether the flow is complete, and whether you can explain it.

Complete

The PR goes from your fork to your partner's oss-practice, it changes one real thing, it has a three-line description, and the issue has both links.

Partial

The PR is inside your own repository instead of to the upstream, or the description is missing, or a link is missing. If two submissions are the same text, both are Partial.

Not submitted

No issue by the deadline. Late work still gets partial credit.
